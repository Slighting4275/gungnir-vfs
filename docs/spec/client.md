# Client behaviour (src/client-zig)

What each GIO module feature does, its threads, budgets and error mapping. Rules that bind all client code are in AGENTS.md §1.A; the wire format is in protocol.md.

- Daemon connection (milestone 3): `instance_init` of the first GungnirVfs reads the socket path from the environment and starts ONE `gungnir-connect` GThread (`g_thread_try_new`), which runs the whole handshake (`ipc.zig` `connectAndPing`: non-blocking connect, hello, ring setup, one ping) within `connect_timeout_ms` (500). The GIO calling thread never touches the socket, and the vfuncs keep delegating to the local VFS whatever the outcome, so a missing or hung daemon can never block or break GIO. The read-only int property `daemon-state` reports 0 connecting, 1 connected (ping ok), 2 unavailable. `g_io_module_unload` joins that thread (bounded by the timeout) and closes the connection. Socket and ring code uses raw `std.os.linux` syscalls with explicit errno checks, and nothing waits without a deadline. Since milestone 6 this lives in `link.zig`: GIO threads share the one connection through `acquire(deadline)`/`release` (a GMutex taken with trylock up to the deadline, a futex wait while still connecting, both bounded by the caller's deadline; one request at a time). A transport failure (`DaemonAbsent` from the zero-timeout liveness poll of the control socket, `Protocol`, `RingCorrupt`) closes the connection and sets `daemon-state` to 2; the next metadata call at least 2 s later starts a fresh connector thread.
- Metadata hooks (milestone 6, `gmeta.zig`): GLocalFile calls the default VFS's private `GVfsClass` slots `local_file_add_info`, `local_file_set_attributes`, `add_writable_namespaces`, `local_file_removed` and `local_file_moved` (GLib `glocalfileinfo.c`/`glocalfile.c`, the same hooks gvfs's GDaemonVfs uses); GungnirVfs fills them, so they only run with `GIO_USE_VFS=gungnir`. `add_info` returns at once unless the matcher asks for `metadata::*` or specific `metadata::<key>`s (`enumerate_namespace`/`enumerate_next`), then identifies the path and fetches all keys (list + get) or just the named ones, adding all of them or none. `set_attributes` handles every `metadata::*` attribute of the info: `string`, `stringv`, `INVALID` = unset, anything else `G_IO_ERROR_INVALID_ARGUMENT`; each attribute is marked `SET` or `ERROR_SETTING` (GLib turns an unmarked one into "not supported"), the first error only is reported. Error mapping: no daemon -> `NOT_SUPPORTED`, busy/ring full -> `BUSY`, deadline/suspect mount -> `TIMED_OUT`, missing file -> `NOT_FOUND`, too many keys -> `NO_SPACE`. `add_writable_namespaces` adds `metadata` (string, copy with file, keep when moved). `removed`/`moved` notify the daemon (best effort). Budgets: 200 ms for a whole query, 300 ms for a set/removed/moved, lock and connection waits included; a query that misses it just has no metadata attributes. On the UI thread (the thread dispatching the default main context, `g_main_context_is_owner(g_main_context_default())`: GTK handlers, idles, and the synchronous GIO calls made from them) every hook gets `ui_budget_ms` (3) instead, to stay within the < 5 ms client-thread SLO (AGENTS.md §4); after any request times out, UI-thread hooks skip the daemon for `ui_quiet_ms` (1000) without waiting at all, and never queue behind a worker that has held the connection longer than `ui_budget_ms`. Worker threads (`query_info_async`, enumerators run in a GTask) keep the full budget, and any answered request ends the quiet period. So a stuck daemon (stopped, or its ring thread waiting out a hung mount for the resolver's 250 ms) costs the UI one 3 ms probe per second, and a UI-thread query then simply has no metadata. Symlinks are identified as themselves (like gvfs's path-keyed metadata). Hook temporaries use `std.heap.c_allocator`, passed explicitly.
- Mount health (milestone 7, `health.zig`): after its ping the connector thread subscribes to mount-health events; a `gungnir-health` GThread drains them while the link is idle (futex wait on the reply ring, bounded), and calls drain them while waiting for a reply. The table (<= 64 mounts, paths <= 1024 bytes, behind a GMutex) is replaced by each complete snapshot; overflow, an incomplete snapshot or a lost connection makes it `unknown`, which defers to the daemon's own gate. `blocks(path)` is a pure lexical longest-prefix lookup, no syscall: never touch a hung path from the module. For paths on hung/gone mounts `add_info` adds no metadata, `set_attributes` fails with `TIMED_OUT` ("...reported by the gungnird mount health monitor") and removed/moved are not sent. GLocalFile's own `stat` still runs before the hooks, so a really hung mount still blocks plain GIO calls; that is GLib's, not ours. The health check comes first, before `link.budget`/`acquire`: on the UI thread too a call under a hung mount costs no wait, and failing it neither waits out `ui_budget_ms` nor starts the `ui_quiet_ms` period (it is not a timeout). The event thread holds the link only to drain the ring and records `held_since` like any holder. Read-only int property `unhealthy-mounts`.
- File operations (milestone 8, `fileop.zig`): GIO has no hook for GLocalFile copy/move/delete (GVfsClass's private slots are metadata-only; GLocalFile's GFileIface and `g_file_copy`'s fallback are GLib's own, behind `G_IS_LOCAL_FILE` checks), so the async engine is exposed as a dynamic GObject type `GungnirFileOp` (registered in `g_io_module_load`, no new export; look it up with `g_type_from_name`). Construct-only props `operation` (1 copy, 2 move, 3 delete, 4 delete-tree, 5 fsync), `source`, `destination`, `flags` (GFileCopyFlags, no BACKUP), `timeout-ms`; action signal `start(GCancellable)` -> gboolean returns at once; `progress(gint64, gint64)` and one `finished(GError*)` are emitted on the caller's thread-default main context. Each op runs on a detached `gungnir-op` GThread with its own connection; every wait is bounded (connect 500 ms, accept 1 s, op timeout + 2 s, 45 s without events, 50 ms slices polling the GCancellable, cancel answered within 2 s). Paths that `health.blocks` are refused with `TIMED_OUT` without a connection; no daemon gives `NOT_SUPPORTED`; <= 16 live ops (else `BUSY`). The first start pins the module (class ref never dropped).
- Trash and recent files (milestone 9, `vfsfile.zig`): `get_file_for_uri` and `parse_name` give a `GungnirFile` for `trash:` and `recent:` URIs, the root or one item (`trash:///h-<entry>`, or `<hex of the trash directory>-<entry>` on another volume; `recent:///<hex of the URI>`). Each call opens its own connection, so a long delete never holds the metadata link; no daemon gives `NOT_SUPPORTED` within the 500 ms connect bound. A mount inside an item is `G_IO_ERROR_BUSY` ("contains a mounted filesystem; unmount it and try again"), items left is `NOT_EMPTY`, a hung volume `TIMED_OUT`, a request refused because every request thread is taken `BUSY`. `g_file_move` from the trash to a local path restores, never overwriting. Inside a trashed folder (`<item>/<path>`) everything can be browsed and read but not changed (`NOT_SUPPORTED`: only whole items have a record); a URI that fails unescaping is no item. Reading an item opens the target on its own `gungnir-open` thread with a 5 s deadline (`TIMED_OUT`; a target on a mount known hung fails at once; at most 32 such threads, then `BUSY`), since `g_file_read` follows links and a FIFO blocks it. One item's info is a stat by name, never a scan. Reads and seeks of an item run on its own `gungnir-stream` thread with a 30 s deadline (`TIMED_OUT`, and the stream stays failed; a cancel answers within 100 ms; 1 MiB per read; at most 32 streams, then `BUSY`). A monitor on a root takes its baseline on a `gungnir-monitor` thread (the creator waits 3 ms on the UI thread, else 200 ms; a late or failed one starts from nothing, so the first round reports everything), polls a stamp every 2 s, lists only when it moved, and emits `CREATED`/`DELETED` on the creator's main context as idle sources, at most 256 waiting (at most 16 monitors; test hook env `GUNGNIR_TEST_READ_TIMEOUT_MS` sets the read deadline, compiled only into the itest's own copy of the module, built with the build option `test_hooks`; the installed `.so` never has it, and CI checks). Every scheme advertised must open at its root (`vfs-uris` itest, BC-HC-F03).
